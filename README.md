# Wishlist (Telegram WebApp)

Мини-приложение для ведения списков желаний в Telegram: веб-интерфейс (WebApp), бот для входа и уведомлений, серверная логика и администрирование доступа.

## Стек

- **Backend:** Python 3.10+, Django, **Django Ninja** (HTTP API, схемы на Pydantic v2), PostgreSQL  
- **Упаковка и качество:** Poetry; pytest, pytest-django; Flake8; mypy  
- **Интеграции:** HTTPX; при работе с Telegram Bot API — пакет **tg-api** (обёртка над HTTPX + Pydantic)  
- **Инфраструктура:** Docker / Docker Compose; CI — GitLab CI/CD  
- **Наблюдаемость:** **Rollbar** — сбор ошибок и стектрейсов (Django-бэкенд; при необходимости клиентский JS во фронте); ключи только через переменные окружения  
- **Асинхронность:** по мере внедрения — async-views/клиенты там, где уместно; учитывать ограничения Django ORM в async-контексте  
- **Frontend (отдельный этап):** React, **TypeScript**

Целевая архитектура — **несколько развёртываемых сервисов** (API, бот, фоновые задачи/уведомления и т.д.) с чёткими границами; на ранних этапах допустим один репозиторий и постепенное выделение контейнеров.

## Контракт аутентификации API (JWT)

Цель: после того как пользователь **получил доступ** (инвайт активирован, есть `TelegramProfile`), не таскать и не перепроверять `initData` на каждый CRUD-запрос. `initData` остаётся **доказательством от Telegram** при открытии WebApp и при продлении сессии; JWT — **билет к API**.

### Роли токенов (нормальный жизненный цикл)

| Токен | Назначение | TTL (дефолт) | Куда класть в запросах |
|--------|------------|--------------|-------------------------|
| **Access** | Вызовы API (`wishlists`, «кто я», …) | **1 час** (`3600` с) | `Authorization: Bearer <access_token>` |
| **Refresh** | Получить новую пару токенов **без** повторного `initData`, пока refresh жив | **30 дней** | Только на эндпоинт refresh (не на каждый CRUD) |

Почему не «одни сутки access без refresh»: украденный access с длинным TTL долго действует от имени пользователя. Короткий access + длинный refresh — обычная практика; для Mini App запасной путь всегда есть — снова открыть WebApp и пройти bootstrap с `initData`.

Имена env (значения только локально / на сервере, не в git):

- `JWT_SECRET` — длинная случайная строка для подписи JWT (отдельно от `SECRET_KEY` Django предпочтительно).
- `JWT_ACCESS_TTL_SEC` — опционально, дефолт `3600`.
- `JWT_REFRESH_TTL_SEC` — опционально, дефолт `2592000` (30 дней).

### Когда выдаём токены

1. **Первый доступ:** успешный `POST /api/telegram_webapp/activate-invite` (`initData` + токен инвайта) → в ответе access + refresh (и метаданные срока).
2. **Повторные открытия WebApp:** после проверки `initData`, если профиль уже есть → bootstrap (отдельная ручка или расширение `verify-init-data`) выдаёт новую пару токенов. Инвайт повторно активировать не нужно.
3. **Access истёк, refresh ещё жив:** `POST` refresh (контракт ручки — в A2) → новые access (+ при ротации — новый refresh).
4. **Refresh истёк / отозван:** только снова `initData` (открытие Mini App) → bootstrap как в п.2.

Не выдаём access/refresh пользователю **без** `TelegramProfile` (не активировал инвайт): валидный `initData` ≠ доступ к продукту.

### Claims и идентификация

- **Access JWT (минимум):** `sub` = **`telegram_user_id`** (строка или число в JSON claim — зафиксировать при реализации), `exp`, `iat`, `type` = `"access"` (или эквивалент, чтобы не принять refresh как access).
- **Refresh JWT (минимум):** `sub` = тот же `telegram_user_id`, `exp`, `iat`, `type` = `"refresh"`; на сервере желательно хранить возможность отзыва (jti / запись в БД) — деталь реализации A2, не блокирует контракт.
- Поиск профиля при обработке API: по **`telegram_user_id`** из `sub`.

Алгоритм подписи: HMAC (например HS256) с `JWT_SECRET`. Не принимать токены с `alg: none`.

### Форма ответа при выдаче / refresh (ориентир)

```json
{
  "access_token": "<jwt>",
  "refresh_token": "<jwt>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_expires_in": 2592000
}
```

`expires_in` / `refresh_expires_in` — секунды **до истечения** с момента выдачи (удобно клиенту для таймера сессии). Допустимо дополнительно отдать абсолютный `exp` в UNIX time.

Клиент для защищённых ручек:

```http
Authorization: Bearer <access_token>
```

### Что защищаем (план A3)

- Ручка «кто я» (профиль / `telegram_user_id`).
- CRUD wishlists/wishes — постепенно с `init_data` в headers на **Bearer** (входные `verify-init-data` / `activate-invite` / bootstrap остаются на `initData`).

### Границы безопасности (важно для Mini App)

- Скрытие кнопки WebApp или `WebApp.close()` — **UX**, не единственная защита. Доступ к данным режет **API** (нет профиля / нет валидного Bearer → 401/403).
- Access-токен не логировать; HTTPS обязателен вне localhost.
- Хранение на клиенте: access можно держать в памяти WebApp на сессию; refresh — осторожно (не в публичных логах; для учебного MVP допустимо согласовать с фронтом позже).

### Вне скоупа этого контракта (backlog продукта)

- Лимит «одна активная инвайт-ссылка на пользователя» при выпуске в админке.
- Удаление/деактивация профиля при отписке от бота с сохранением записи Invite — отдельная фича бота (`my_chat_member` и политика данных).
